# B1–B6 并列执行与完成台账

本文记录 B（后端数据/API）可独立完成的工作、可并列推进的批次，以及必须由 A/C/D/E 提供的联合证据。它不替代 [B 后端执行计划](B-BACKEND-PLAN.md)、[HTTP 合同](API.md) 或 [联合交接说明](B-INTEGRATION-HANDOFF.md)。

## 并列原则

- 同一波只并列互不依赖、写入文件不重叠的任务。
- 下一波只在上一波产物可读取后开始，避免按假设审查尚未完成的实现。
- B 可独立完成“接口、数据、测试、工具、说明”；不能把 A 的浏览器画面、C 的真实模型、D 的质量签字或 E 的发布候选冒充为 B 已完成。
- 所有完成结论绑定具体提交和可重跑证据；聊天里的口头结论不是发布证据。

## 第一波：B 能直接实现的四条线

| 并列线 | 范围 | 产物 | B 侧完成判定 |
|---|---|---|---|
| B1/B2 接口与并发 | HTTP、幂等、版本、失败语义、持久化 | 实现、合同测试、逐项审计 | HTTP 可见行为和 SQLite 提交竞争都通过 |
| B3 前端合同 | TypeScript 请求/响应与错误收窄 | `contracts/api.ts`、编译期调用示例、CI | A 不读后端源码即可正确分支处理 |
| B4 浏览器接线准备 | A 的启动、代理、token、422/409、重启步骤 | A 联调手册 | 每一步都可由当前端点和已有运行模式执行 |
| B5/B6 发布门槛 | B 侧检查、敏感文件检查、统一机器可读结论 | 一键验证器及测试 | 任一子检查失败时整体非零退出且不产生假阳性 |

第一波完成后，不直接宣布 B1–B6 全部完成；先进入第二波交叉验证。

## 第二波：交叉验证

| 并列线 | 验证重点 | 输出 |
|---|---|---|
| 合同一致性 | 运行时 JSON、`docs/API.md`、TypeScript 类型和调用示例是否一致 | 字段/状态码差异或通过结论 |
| A 手册可执行性 | 从停止状态启动，普通闭环、危险、422、409、重启是否无需改代码 | 后端侧演练证据；浏览器证据仍由 A 提供 |
| 发布验证器故障注入 | pytest、Mock、demo、TypeScript、Git 清洁检查任一失败能否被阻断 | 聚焦测试和 JSON 结果 |
| 角色交接复核 | A/C/D/E 的输入、输出、负责人、禁止越界和完成证据是否明确 | 缺项清单或通过结论 |

第二波发现问题时直接修复并回归；修复完成后进入第三波最终冻结检查。

## 第三波：B 侧最终冻结

第三波在同一个 B 提交上执行：

```bash
python -m pytest -q
python -m backend.evaluate_mock
python -m scripts.demo
npm ci
npm run check:contracts
```

同时验证：

- B1–B3 的每项验收要求都有代码、测试或合同证据。
- B4 的后端联调条件和 A 手册完整；A 的真实浏览器证据明确标为外部待交付。
- B5 的 A/C/D/E 双向交付说明完整。
- B6 的 B 侧发布门槛可一键运行；唯一发布候选、前端浏览器、真实模型或明确 Mock 决策、备份恢复仍由对应负责人签收。
- Git 不跟踪 `.env`、密钥、运行数据库、缓存或依赖目录。
- 最终再做 Standards/Spec 双轴评审，剩余发现为零。

## 不得提前打勾的项目

- 未看到 A 的实际页面，不写“浏览器联调完成”。
- 未看到真实供应商调用，不写“真实模型验证完成”；选择 Mock 时必须明确标注。
- 未看到 E 的唯一候选提交和备份恢复，不写“比赛版本已冻结”。
- 软件回归不能表述成临床安全、诊断准确或真实用户验证。
