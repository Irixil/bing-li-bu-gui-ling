## 3. A/C/D/E 与 B 的双向交付

### A：老人端前端

**B 提供给 A**

- 固定端点、请求头、状态码、错误码和 TypeScript 类型。
- 保存、整理、核对、修订、历史和交接快照的状态迁移说明。
- 可复现的普通、危险、`422`、`409`、幂等和后端重启联调方法。
- 联调期间只修影响冻结合同或核心闭环的后端问题。

**A 交给 B**

- 浏览器完成核心闭环的证据：普通记录、危险记录、整理、核对、历史、修订和交接材料。
- `422` 页面证据：明确显示“原文已保存，AI 整理失败”，原文、危险提醒和重试入口仍在。
- `409` 页面证据：重新获取详情并让用户重载或修订，没有静默覆盖。
- 刷新与后端重启证据：记录从 GET 恢复；服务重启后重新读取 `/health` 获取 token。
- 如果需要新字段，提交字段用途、页面位置和无法由现有字段实现的原因，由 B 评估后更新合同。

**边界**

- A 负责页面、视觉、交互和前端状态，不直接改变后端状态机或复制一套后端字段定义。
- B 不替 A 重写页面；A 不把“医生确认”“医学正常”“风险已解除”等错误医疗含义写进 UI。
- 前端不得把 `recorded_at` 当用户输入提交；发生时间不确定时保留 `occurred_time=null`。

### C：AI、提示词与危险规则

**B 提供给 C**

- 模型适配器进入后端后的输入边界、成功草稿 Schema 和固定 HTTP 包装格式。
- 原话先保存、失败写审计、旧草稿不被失败结果覆盖、本地危险提醒不能被模型抵消的持久化保证。
- 成功与失败适配器的接口级测试接缝；只 Mock 外部模型供应商。

**C 交给 B**

- 一条真实模型成功证据：使用哪一配置、返回结构是否通过 Schema/来源/时间/安全校验；证据不得包含密钥或完整供应商敏感正文。
- 一条真实模型失败证据：断网、超时、非法 JSON 或模型异常进入冻结的 `422` 语义，原文和本地危险状态仍可查询。
- 提示词、模型配置和危险规则变动对应的测试，以及新增误报/漏报的已知限制。
- 若真实模型在比赛前不稳定，明确交给 E 使用 Mock 的备用决策，不把 Mock 宣称为真实模型。

**边界**

- C 负责 `backend/adapter.py`、`backend/safety.py`、`prompts/`、`config/` 的模型与规则内容，不直接改数据库结构和记录状态机。
- C 不改变 B 冻结的 HTTP 字段和错误语义；确需改变时先向 B 提合同变更。
- 模型不得生成诊断结论、自动改药建议、虚构来源或虚构日期；本地危险命中不得被模型降级。

### D：数据与质量

## 4. 固定联调样例

以下样例描述顺序和判定点；完整字段仍以 [API.md](API.md) 为准。

### 4.1 会话与保存

1. `GET /health`，保存响应中的 `session_token`。
2. `POST /api/events`，请求头带：
   - `Content-Type: application/json`
   - `X-Session-Token: <本次进程返回的 token>`
   - `Idempotency-Key: <crypto.randomUUID()>`
3. 普通输入：

```json
{
  "raw_text": "今天散步二十分钟",
  "source_kind": "elder",
  "actor_name": "老人"
}
```

首次成功应为 `201`、`created:true`、`event.state:"inbox"`、`event.version:1`。页面此时立刻显示“已保存”，不等待整理。

同一次请求超时重试必须复用同一个幂等键和完全相同的请求体；成功应为 `200`、`created:false`，且 `record_id` 不变。同一幂等键换请求体应为 `409`。用户主动新建另一条记录时必须生成新键，即使文字相同也应保留为新记录。

### 4.2 整理、核对与修订

```json
POST /api/events/{record_id}/organize
{"expected_version":1}
```

整理成功为 `200`，事件进入 `draft`，版本加一；前端显示草稿仍待核对。随后用服务器刚返回的版本调用：

```json
POST /api/events/{record_id}/review
{"expected_version":2,"action":"confirm","note":"仅确认记录准确"}
```

核对成功进入 `recorded`，但 `local_safety` 不被清除。修订必须带旧记录当前 `expected_version`、新原文、来源、记录人和原因；成功 `201`，返回新 `record_id`，新记录版本从 1 开始，旧记录变为 `superseded` 且旧原文仍可查询。

### 4.3 危险提醒与 `422`

使用危险输入：

```json
{
  "raw_text": "今天胸口疼，喘不上气",
  "source_kind": "elder",
  "actor_name": "老人"
}
```

保存成功响应中的 `event.local_safety.danger_detected` 应为 `true`，固定 `danger_reminder` 必须在页面顶部显示。之后即使整理失败、核对成功或生成交接材料，提醒也不能被隐藏或清除；交接材料应保留未解决危险原因。

让模型适配器返回断网、超时或非法 JSON，再调用整理。HTTP 应为 `422`，但响应仍是业务可用数据，至少包含：

```json
{
  "ok": false,
  "error": "ai_organize_failed",
  "ai_failed": true,
  "raw_text_preserved": true,
  "failure_reason": "可展示的失败原因",
  "event": {},
  "local_safety": {},
  "danger_detected": true,
  "escalation_level": "emergency",
  "review_role": "emergency_services",
  "danger_reminder": "原始记录中出现需要及时人工或急救专业人员判断的描述，请联系当地急救服务或专业人员，不要自行改药。"
}
```

调用方必须先解析 JSON，再判断 `response.ok`。第一次整理失败时事件保持 `inbox`，不能伪造草稿；已有旧草稿时，本次失败保留旧版本和旧草稿，页面要注明“本次重新整理失败”，不能把旧草稿冒充本次结果。

### 4.4 `409` 版本冲突

1. 先 GET 详情并记住当前 `event.version`。
2. 用该版本成功执行一次写操作，使服务器版本前进。
3. 再用旧版本调用整理、核对或修订，应得到 `409` 和 `error:"stale_version"`。
4. A 重新 GET 详情，提示用户重载或基于最新记录发起修订；不得自动覆盖。

冻结合同要求整理、核对和修订都必须提供正整数 `expected_version`：缺失、布尔值、字符串、零或负数应为 `400 expected_version_must_positive_integer`。基线提交 `e1a5967` 的整理接口对“缺失”会代取最新版本；当前 `fix/backend-api` 已修复并加入接口测试，合并到发布候选前仍不得把它写成团队基线已验证。

### 4.5 token、重启与持久化

`session_token` 属于当前后端进程，不得写死或提交。后端重启后：

- 旧 token 不再有效；调用方重新 `GET /health` 获取新 token。
- SQLite 中已提交的记录、原文、危险状态、历史与交接快照应继续存在。
- `403` 可能是 token 或 Origin 错误；先核对后端是否重启和 `ALLOWED_ORIGIN`，不要把它当作数据丢失。

本地数据库默认在 `runtime/records.sqlite3`。数据库无法写入时，不得显示“已保存”。

## 5. 错误语义速查

| HTTP | 含义 | 调用方动作 |
|---|---|---|
| `400` | JSON、字段或请求格式错误；包括冻结目标中的非法 `expected_version` | 保留输入，显示可修正字段；不要自动重试同一错误请求 |
| `403` | 本地 session token 或 Origin 不被接受 | 后端重启后重新取 token；同时核对前后端地址与 `ALLOWED_ORIGIN` |
| `404` | 记录或交接材料不存在 | 回到列表并刷新；不要生成空白假记录 |
| `409` | `stale_version`、非法状态迁移或幂等键与请求体冲突 | 版本冲突时重新 GET；幂等冲突时检查是否错误复用了键 |
| `422` | AI 整理失败，不等于原话保存失败 | 解析并保留响应体，展示已保存原文、失败原因、危险提醒和重试入口 |
| `500` | 未预期的服务端错误；响应不包含内部异常细节 | 保留页面输入，不显示“已保存”；记录复现步骤交给 B |
| `200/201` | 操作成功；创建重试可能是 `200 created:false` | 以响应中的事件 ID、状态和版本更新 UI |

一般错误为 `{ok:false,error:"错误码"}`。错误页面不得泄露密钥、供应商原始响应、内部堆栈或数据库路径。

## 6. 公开病例统一口径

比赛中的公开资料是 **1 位公开论文病例患者的 3 段改编摘要**，不是 3 位患者、不是医院原始病历、不是逐字患者自述，也不是本项目真实用户测试。

- 来源论文与作者署名、DOI、PMCID 和 CC BY 4.0 许可见 [公开病例说明](../data/public_cases/README.md)。演示材料必须保留署名、来源和许可。
- 本项目只做节选、中文翻译和概括，并省略部分背景、诊断、治疗和影像。
- 三段输入均用 `source_kind:"document"`；其中“女儿报告”仍是论文摘要内容，不能说成本项目收到女儿直接发言。
- 发生时间保持 `null`，不得虚构绝对日期；导入时间只是本次演示的记录时间。
- 第 1 段胸闷/活动后气短会命中本地危险提醒。
- 第 2 段心率每分钟 40 次是当前规则已知覆盖缺口；`expected_local_danger:false` 只表示未命中关键词，绝不表示医学正常。
- 第 3 段同样不能因未命中本地规则而解释为“没有危险”。

普通生活输入、断网输入和 40 条回归数据属于 synthetic/mock，必须与公开病例分开说明。

## 7. 分支、PR 与合并顺序

推荐分支保持：

- A：`feat/elder-ui`
- B：`fix/backend-api`
- C：`feat/model-safety`
- D：`test/public-cases`
- E：`chore/demo-integration`

同步开发时按以下顺序收口：

1. **B 先合并合同底座。** B1/B2/B3 分成垂直 PR；凡接口变化，同一 PR 同步实现、HTTP 测试、[API.md](API.md) 和 [contracts/api.ts](../contracts/api.ts)。
2. **C、D、A 基于已合并合同依次收口。** C 的模型/规则、D 的数据/验收、A 的页面都可提前并行开发，但提交合并前先更新到最新主分支并消除第二套字段定义。互不冲突的 C/D PR 可由 E 调整先后；任何接口依赖都以 B 先合并为准。
3. **A 完成真实浏览器闭环后再宣称网页可演示。** B 与 A 共同确认 `422`、`409`、危险提醒和重启 token。
4. **E 最后合并启动、备份和演示材料。** E 记录唯一发布候选提交号，从停止状态重新执行冻结验收。

每个 PR 只交付一个垂直行为，不夹带大规模格式化、框架迁移或他人模块重写。PR 必须写清：改了什么、A/C/D/E 如何接、实际运行了哪些检查。五个人都通过 PR 合并，不直接并发推送 `main`。

发生冲突时，由文件负责人判断业务语义，E 负责执行合并：HTTP/数据库由 B，模型/规则由 C，病例和验证口径由 D，页面由 A，启动与演示由 E。合并工具不得替代负责人判断。

## 8. 比赛冻结门槛

E 只能在同一个发布候选提交上逐项打勾；任一硬门槛失败，版本保持“候选”，只修导致核心演示失败的问题。

### 8.1 后端硬门槛

```bash
python -m pytest -q
python -m backend.evaluate_mock
python -m scripts.demo
npm ci
npm run check:contracts
```

依赖已安装后，也可运行 `python -m scripts.verify_b_release` 一次执行上述 B 侧检查并取得机器可读 JSON。它会强制使用 Mock、移除凭据类环境变量并检查 Git 路径，但不代替浏览器联调、真实模型或明确 Mock 决策、备份恢复和全流程排练。

- 全部命令成功，结果绑定发布候选提交号。
- TypeScript 合同使用锁定版本依赖严格编译，A 不需要从后端源码猜字段。
- 创建幂等、版本竞争、修订历史、交接快照不可变和 SQLite 重启恢复有可重复证据。
- 整理缺失/非法版本为 `400`、旧版本为 `409`；`422` 保留原文与危险提醒。
- `git status` 和 PR 暂存清单不含 `.env`、token、运行数据库、缓存、依赖目录或密钥。

### 8.2 浏览器硬门槛

- A 在比赛实际浏览器跑完普通保存 → 整理 → 核对 → 历史 → 修订 → 交接材料。
- 危险输入的固定提醒始终可见，核对后仍保留。
- AI 失败页面正确处理 `422`，旧版本页面正确处理 `409`。
- 页面刷新能恢复记录；后端重启后重新获取 token 并恢复 SQLite 数据。
- 至少完成一次从前后端都停止的状态启动，不临场修改代码或数据库。

### 8.3 模型与备用方案门槛
