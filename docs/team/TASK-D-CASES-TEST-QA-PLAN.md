## 1. 任务 D 的一句话目标

把团队做出来的功能变成一套**可重复演示、可验证、不会夸大能力的交付物**。

D 负责三件事：

1. 准备有来源、许可依据和用途明确的病例及测试材料，并把最终使用范围交由相应负责人确认。
2. 按用户真实操作路径测试系统，记录预期与实际差异。
3. 在比赛或发布前根据证据整理“通过”“部分完成”和“尚未验证”的建议，供项目负责人决定对外口径。

D 不负责：

- 编写媒体保存、数据库、AI 接口或前端页面；
- 修改医学结论、替用户判断疾病；
- 把 Mock 结果包装成真实模型结果；
- 自行购买服务、上传私人医疗资料或发布公网服务；
- 代替 E 或项目负责人合并 `main`、发布或备份代码。
- 冻结媒体/API 合同，或代替相应负责人作出最终医学、法律、产品和发布决定；D 只检查依据并提出建议。

## 2. 当前基线和工作边界

当前主分支已经有文字记录闭环：

```text
输入原话 → 保存原文 → 本地危险扫描 → 文字整理 → 人工核对
→ 历史/修订 → 就诊交接材料
```

当前还没有：

- 录音和照片上传；
- 媒体原件保存、读取和恢复；
- 真实 ASR/OCR；
- 完整老人端网页和手机验收。

因此 D 的工作分为两条线：

- **现在即可做**：公开病例整理、文字后端基线测试、测试方案、验收表和证据规范；
- **等待开发完成后做**：媒体、前端、手机和最终整体验收。

## 3. D 的交付物

### 3.1 公开病例登记表

记录“这个案例从哪里来、依据是什么、拿来测什么”；最终许可和对外使用范围由项目负责人或相应责任人确认。

每条至少记录：

| 字段 | 说明 |
|---|---|
| `case_id` | 稳定编号 |
| `case_group` | 是否属于同一患者/同一资料 |
| 来源 | URL、作者、DOI/PMCID |
| 许可 | 许可类型、署名要求、核验日期 |
| 改编说明 | 节选、翻译、概括、脱敏了什么 |
| 输入内容 | 实际送入系统的文字或媒体 |
| `source_kind` | 例如 `document`、`audio_transcript` |
| `occurred_time` | 不确定时保留 `null` |
| 预期结果 | 是否应出现危险提醒、应保留哪些字段 |
| 已知限制 | 哪些结论不能从该案例推出 |

当前项目已有 1 位公开论文患者、3 段同一病例摘要。它们足够做当前演示，不需要为了“数量好看”继续搜集大量病例。只有当新案例覆盖了现有资料没有覆盖的场景时，才增加案例。广泛的结构和异常测试优先使用 `data/synthetic/` 合成数据。

### 3.2 测试矩阵

回答“什么时候、用什么输入、按什么步骤、应该看到什么”。

建议字段：

| 字段 | 说明 |
|---|---|
| 用例 ID | 例如 `TEXT-SAVE-01` |
| 测试阶段 | 当前文字、媒体联调、手机验收等 |
| 前置条件 | 提交号、服务、数据库状态 |
| 输入 | 案例编号或故障注入方式 |
| 操作步骤 | 可复现的点击或命令 |
| 预期 | 必须看到的用户可见结果 |
| 实际 | 实际发生的结果 |
| 证据 | 日志、JSON、截图、录屏、校验和 |
| 状态 | 通过、失败、阻塞、待确认 |
| 缺陷号 | 失败时关联问题 |

### 3.3 缺陷记录

每个问题都写清：版本、输入、步骤、预期、实际、影响、是否阻断比赛演示、证据位置和建议负责者。

### 3.4 阶段验收报告

最终报告不只写“测试通过”，而要分别写：

- 已交付；
- 条件式交付；
- 等待决定；
- 明确不在本次范围。

### T1：公开病例资料包（已建立资料包；最终口径仍需确认）

目标：让每条案例有来源、许可依据、用途和可复核的预期行为与限制。

你亲自做：

1. 审阅来源页面和许可文字，记录依据；最终许可判断由相应负责人确认。

3. 整理改编说明、署名和限制写法，提交负责人确认。
4. 为每条案例写产品层面的“预期系统行为”，特别是危险提醒和时间不确定性，不作医学结论。
5. 提出对外展示用语建议；最终产品和法律口径由负责人确认。

可以交给 Agent：

- 从公开来源提取作者、DOI、PMCID、许可链接和章节位置；
- 按现有 `cases.json` 格式整理字段；

- 许可是否足够；
- 医疗表述是否可以对外使用；
- 是否把某句话写成患者本人说的；
- “未命中危险规则”是否可以说成安全。

T1 的通过条件：

- 当前至少有一份可重复使用的公开病例登记表；
- 每条都有来源、许可、改编和预期结果；
- 公开病例、合成样例、真实授权媒体分开；
- 不把论文改编说成真实用户或临床测试。

### T2：现有文字功能基线（已有可用准备；尚未完整验收）

目标：在媒体功能开发前，先确认旧功能没有误解，并留下基准结果。

你亲自做：

1. 用一条普通记录走完整流程。
2. 用胸闷/气短案例检查危险提醒。
3. 用心率 40 案例检查“未命中不等于正常”的表达。
4. 检查人工核对不会清除危险提醒。

可以交给 Agent：

推荐基线命令：

```bash

python -m backend.evaluate_mock
python -m scripts.demo --out runtime/demo-result.json
```

T2 的通过条件：

- 有一份当前提交的基线结果；
- 已验证和未验证项分开记录；
- 任何失败都能复现或明确是环境问题；

当前状态：公开病例、文字基线、失败重试和病例引用动态校验均已有可复核证据；仍需在最终集成基线上统一复测，因此 T0–T2 只能称为“可用准备”，不能称为完整验收。

Mock 结果口径：`40/40` 指 40 条合成样例的结构校验通过；其中指定的 6 条危险样例为 `6/6` 安全断言通过。它不表示 40 条业务语义全部正确，也不表示真实模型质量或临床安全。

### T3：开发期间的合同和 PR 检查（B/C/前端开发期间持续进行）

目标：尽早发现“功能做出来了，但各人理解不一样”的问题。

5. 逐个 PR 判断是否有足够测试和交接说明。

可以交给 Agent：

- 找出文档写了但代码没有的端点；
- 根据字段和状态自动生成测试用例草稿；
- 检查是否泄露密钥、绝对路径、数据库或私人媒体；

重要边界：`MEDIA-CONTRACT.md` 目前是草案。合同由相应负责人/集成人冻结；冻结前 D 只能准备测试、检查差异并提出验收意见，不能宣布媒体接口可验收。

- 每个 PR 有运行方式、测试结果和未完成事项；
- E 负责合并，D 负责提出通过/阻塞意见。

### T4：媒体后端合并后的集成测试（A/B PR 合并后，约 1–2 天）

目标：验证媒体从原件到就诊交接没有断点。

你亲自做：

1. 在干净数据库上执行成功路径。
2. 逐项执行失败、重试、重启、并发和版本冲突场景。
3. 检查用户看到的状态和提示是否准确。
4. 评估问题对比赛展示的影响并提出是否阻断的建议；最终是否阻断由项目负责人决定。

可以交给 Agent：

- 生成临时音频、图片和损坏文件测试夹具；
- 执行 API 黑盒测试、重复请求和并发请求；
- 注入超时、空文字、非法响应和网络失败；
- 比较原件、机器初稿、人工修改前后的哈希和内容；
- 执行数据库与媒体备份恢复；
- 汇总日志、响应、截图和校验和。

必须验证：

```text
上传
→ 原件已保存
→ 识别
→ 机器初稿已保存
→ 危险扫描
→ Event 关联
→ 整理
→ 人工核对
→ 修订/历史
→ 交接材料
→ 备份恢复
```

关键失败场景：

- 上传中断；
- 识别超时或服务不可用；
- 空识别结果；
- 伪造文件类型或损坏文件；
- 同一请求重复提交；
- 丢响应后重试；
- 处理中重启；
- 人工修改后旧识别结果迟到；
- 同一版本被两个请求同时修改。

T4 的阻断条件：

- 原件丢失；
- 重试生成重复 Event；
- 机器结果覆盖人工修改；
- 危险提醒消失；
- 失败后无法找回或重试；
- 备份无法恢复。

### T5：前端、浏览器和手机验收（前端接入后，约半天到一天）

目标：确认真实用户操作时不会把状态和结果看错。

5. 在受控手机环境测试录音、拍照权限和 HTTPS。
6. 测试长时间无声先提醒、无回应再暂停、继续录音不丢前后内容。

可以交给 Agent：

- 生成浏览器操作清单和截图标注；
- 运行可重复的浏览器 smoke test（如果有受控浏览器环境）；
- 检查前端请求字段、状态码和错误分支；
- 汇总不同设备/浏览器的结果。

由 D 或指定验收人员核查；最终口径由项目负责人确认：

- 手机麦克风/相机权限；
- 真实触控体验；
- 录音暂停和续录是否符合预期；
- 最终演示文案是否夸大，并将修改建议提交项目负责人确认。

不得恢复已经撤回的“60 秒强制结束”规则。

### T6：比赛演示和发布验收（所有功能通过后；D 提供建议）

可以交给 Agent：

- 生成最终测试报告和证据索引；
- 检查演示脚本与实际接口是否一致；

最终由项目负责人/集成人确认，D 提供验收与发布门禁建议：

## 9. 最终判断标准

只有同时满足以下条件，D 才能建议“本次范围内通过”；最终对外宣布由项目负责人确认：

1. 原文/原件不会丢；
2. 来源和时间不被编造；
3. 保存、识别、整理、核对四种状态分开；
4. 危险提醒不会因核对或修订消失；
5. 失败可以找回、解释和重试；
6. 重复请求不会制造重复记录；
7. 原件、机器初稿和人工修改可追溯；
8. Mock 和真实服务明确区分；
9. 备份可以恢复；
10. 每项结论都有对应证据。

临床安全、真实老人效果、付费意愿和公网生产安全不属于本计划可以单独证明的内容。
