# 当前项目整理与五人计划

整理日期：2026-09-12。下面区分用户已明确的范围与建议安排。功能实现和验证结论以代码及 VALIDATION.md 为准，计划不冒充完成情况。

## 一句话方向

给老人自己用的健康记录本：把今天发生的事情和已有资料留下来，下次就医可以带着连续记录说清楚，不必每次从头回忆。老人不必长期吃药才有使用价值。

比赛展示先证明“记录不会丢、来龙去脉能看懂、危险描述能被提醒、下次沟通能带走一份资料”。订阅只是下一步的收费假设，MVP 不做订阅支付。

## 已明确的范围

- 明天展示一个能跑的 MVP。
- 老人本人为主，不以多个子女协作为本次前提。
- 用户单独负责前端，其他人围绕固定接口并行；本轮助手只修改后端。
- 加离线危险描述兜底，保留安全规则、历史、幂等和交接卡逻辑。
- 真实数据来自明确允许使用的公开病例，合成数据明确标注。
- 使用 GitHub 仓库 `Irixil/bing-li-bu-gui-ling` 共享开发材料。

## 产品闭环判断

后端已经具备并实际跑过这条链：输入原话 → 保存并返回本地提醒 → 模型或 Mock 整理 → 核对记录是否准确 → 查历史 → 必要时新增修订 → 生成就诊交接材料。重复提交不会重复建记录；旧原文和旧交接材料保持可查。

这里的“核对准确”是老人确认自己的话有没有被记错，**不能说是医生审核、诊断确认或治疗批准**。`review_role=family` 是旧接口里的枚举，本 MVP 页面应展示“请核对记录”；不要求增加子女端。专业复核字段暂时是提醒和待办，不代表产品已经连接了医生。

完整产品还没有闭环：前端没有交付，真实模型在新包上未验，公开病例只有一个人，也没有观察真实老人使用。因此当前可称“后端流程跑通”，不能称“临床验证通过”“真实用户留存成立”或“比赛网页已经可用”。

## 五人分工建议

人员姓名尚未提供，先按位置认领。A 已确定是项目负责人本人，B–E 是推荐安排，团队可以调整。

| 人员 | 负责什么 | 主要目录 | 交给别人什么 | 完成标准 |
|---|---|---|---|---|
| A：你 | 老人端前端、讲解时看到的界面 | `frontend/` | 输入、记录列表/详情、核对/修订、交接材料页面 | 实际浏览器能完成核心流程，422 时仍看到危险提醒和已保存原文 |
| B：后端数据/API | 记录、修订、历史、交接材料、接口兼容 | `backend/server.py`、`backend/store.py`、`contracts/` | 不变的请求/响应和状态 | 版本冲突正确、重复提交不重复、数据能重启恢复 |
| C：AI/规则 | 模型接线、提示词、结构和安全校验 | `backend/adapter.py`、`backend/safety.py`、`prompts/`、`config/` | 一条真实模型成功证据及失败证据 | 不编造原文来源/日期、不自行改药；失败不丢原文 |
| D：数据/质量 | 公开资料许可、改编核对、用例和验收 | `data/`、`tests/`、`docs/VALIDATION.md` | 可追溯案例与可重复测试报告 | 样例明确真假，测试跑通，发现漏报不能写成正常 |
| E：集成/演示 | Git 合并、启动环境、演示脚本、备份和讲稿 | `scripts/`、`.github/`、`requirements*`、README | 一份现场能启动的版本和备用方案 | 新目录安装后可运行，断网演示可复现，数据库有备份 |

现有后端改动和脚本让 B、C、D、E 可以从维护与补证据开始，不必重复从零开发。A 现在可直接使用 Mock 接线，不需要等真实模型。

共享接口由 B 收口。C 不直接改数据库；D 不擅自改接口字段；E 不在合并时重写业务逻辑。A 需要新字段先在合同中提出，B 确认后一起改实现与示例。大家不要同时修改同一个大文件。

推荐分支：`feat/elder-ui`、`fix/backend-api`、`feat/model-safety`、`test/public-cases`、`chore/demo-integration`。每个人先 `git pull`，创建自己的分支，提交后推分支，通过 PR 合并到 main。E 负责合并顺序。不要五个人直接往 main 同时推。

PR 写清楚三件事：改了什么、别人要怎样接、实际怎样测过。接口更名必须同时更新 API.md、contracts/api.ts 和调用方。合并后至少运行 `python -m pytest -q` 与 `python -m scripts.demo`。

## 今晚到明天的顺序

1. **先固定底座与资料口径。** 所有人拉取同一仓库。A 读 API.md；其余人确认能启动后端、跑测试，不先加功能。
2. **A 与 C 并行。** A 用 Mock 做最短操作路径，C 在自己的 `.env` 接真实模型。B 只修阻塞接线的问题，D 核对测试资料与输出，E 准备启动与备份。
3. **集中接线一次。** 输入一条普通记录、公开病例危险描述各一条，跑保存、整理、核对、历史、修订、交接材料；让页面展示一次 AI 失败且原文仍在。
4. **冻结演示版本。** 先保住现有闭环，冻结后只修会导致演示失败的问题。子女端只有所有核心验收已过、且仍有余量才考虑，不作为默认加项。
5. **比赛前完整排练。** 在比赛电脑实际从停止状态启动；检查页面、网络、模型配置、字体放大、危险提醒、备用数据及数据库备份。至少一次不用临场手动改代码。

## 比赛建议演示顺序

建议控制在 3–5 分钟。先用“今天散步二十分钟”展示快速记事；再用公开病例的胸闷/气短摘要展示来源、时间不确定和危险提醒；核对记录后证明危险没有自动消失；最后生成就诊材料，并演示修订后旧版本仍能找到。

模型不可用的备用演示可以直接运行指定失败测试，让后端返回 422 并保留原文；前端验收时再接上错误状态。现场如果用 Mock，明确说“当前切换到离线演示模式”；不能把模拟模型返回当成云端 AI 实时结果。

## 目前仍存在的漏洞和不足

- 危险规则覆盖有限。否定、历史、假设句可能误报；没列入的表达和数值可能漏报。心率数值就是公开样例里的已知缺口。未命中不得显示医学安全结论。
- 医生/护士没有进入系统完成专业复核。只可把资料带去给专业人员看，不能展示“医生已确认”。
- 当前本地旧兼容接口没有强制账号鉴权，不能当成多个家庭隔离服务；账号中的 `elder` 角色也尚未覆盖全部整理/修订权限。本 MVP 采用单人本地会话，不做账号 UI。
- 来源检查能够拦截不在输入里的引用 ID 和文字，但“某句引用精确属于哪个历史 ID”的绑定仍不完整；来源类型由输入提供，不代表身份核验。
- 记录时间仍兼容客户端传入值；前端不要提交 `recorded_at`，默认使用服务端时间。发生时间不清楚就保留空值。
- 只保证已被后端接收且数据库可写的有效输入持久化。电脑故障、磁盘损坏、后端未运行不能靠模型失败兜底解决；本地备份另行负责恢复。
- 没有真实老人使用反馈、医学专家验收、付费数据或规模测试。公开病例可以验证软件流程，不能代替这些证据。

如果今天只能再做一件事，优先把老人端最短流程接通并排练。比增加子女、订阅支付或新页面更直接影响明天能不能展示。
