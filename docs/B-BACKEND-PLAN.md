## B 的目标

让 A 能只依赖一份稳定接口完成老人端核心流程，并让 C 的模型结果、D 的验收数据、E 的演示与备份都经过同一套可重复验证的数据规则。

B 不以“新增多少后端功能”为完成标准。B 的完成标准是：接口不需要猜、失败不丢数据、并发不覆盖、重启不丢记录、前端能完成比赛闭环。

## B 负责与不负责

### 负责

- HTTP 请求、响应、请求头、状态码和错误码的一致性。
- 记录创建、幂等、状态迁移、乐观版本、修订和历史。
- SQLite 持久化、不可变证据、审计和交接快照。
- AI 成功/失败进入数据库和 HTTP 后的语义。
- `docs/API.md` 与 `contracts/api.ts` 的同步。
- A 接线期间的后端阻塞修复，以及合并前回归证据。

### 不负责

- 前端页面与视觉交互，由 A 负责。
- 模型选择、提示词质量和危险词规则内容，由 C 负责。
- 公开病例许可、临床口径和验收数据设计，由 D 负责。
- 比赛电脑启动、备份、合并节奏和演示讲稿，由 E 负责。

B 可以拒绝越界改动进入接口冻结版本，但不能替其他角色直接重写其模块。

不为私有函数、SQL 语句或内部调用次数写测试。

## 已发现的接口收口问题

下面是计划输入，不代表现在已经修复：

1. `contracts/api.ts` 目前只有事件、保存响应和整理失败类型，缺少请求体、整理成功、核对、修订、历史、审计、交接材料和通用错误类型。
2. 整理接口在缺少 `expected_version` 时会自动采用当前版本，与文档“写操作用版本防覆盖”的要求不一致。
3. 浏览器跨域预检没有接口级测试；A 使用开发代理时通常绕过，但直连 `ALLOWED_ORIGIN` 时需要验证完整预检响应。
4. 现有 HTTP 测试集中在离线安全，尚未以一份合同测试覆盖全部核心端点和常见错误。
5. 40 条合成数据当前主要验证 Schema 可通过和 6 条危险升级，不能被表述成 40 条语义金标准全部通过。

### B1：建立完整 HTTP 合同测试

状态：B 侧已完成。当前分支已加入核心 HTTP、CORS/Origin、成功/失败交错的并发版本竞争和进程重启合同回归，全量 113 passed；Matt 双轴评审无剩余发现，待合并确认。

这是第一项代码工作。新建独立的接口合同测试文件，通过真实临时 HTTP 服务覆盖：

- `/health` 与本地会话 token。
- 创建成功 `201`、同请求重试 `200`、同键异内容 `409`。
- 列表、详情和不存在记录 `404`。
- 整理成功、整理失败 `422`、缺少/过期版本。
- 核对成功、非法状态、退回原因必填。
- 修订生成新 ID、旧记录变为 `superseded`、旧原文仍可查询。
- 历史和审计可读取。
- 交接快照生成后不可随记录修订而变化。
- 允许来源的跨域预检与错误 Origin。

做法：每个行为独立走一次“失败测试 → 最小实现 → 相关测试通过”，不先批量写完所有测试。

验收：测试只通过 HTTP 观察 HTTP 行为；内部实现重排不需要改测试。

### B2：收紧乐观版本合同

状态：B 侧已完成并通过接口层与 113 项全量回归；Matt 双轴评审无剩余发现，待合并确认。

先增加“整理缺少 `expected_version` 返回 400”的失败测试，再改最小实现。核对和修订保持相同规则：

- 缺失、布尔值、字符串、零或负数：`400 expected_version_must_positive_integer`。
- 与当前版本不一致：`409 stale_version`。
- 服务器不得在调用方缺失版本时自动选择最新版本。
- 两个 HTTP 请求用同一版本并发提交时，数据库至多允许一个成功，另一个返回 `409 stale_version`。

验收：并发提交同一版本时至多一个成功；A 能根据 409 重新获取详情。

### B3：补全并冻结前端 TypeScript 合同

状态：B 侧已完成。TypeScript 合同、HTTP 行为、Schema 与文档已完成核对，锁定依赖的严格编译已进入 CI；待 A 使用验证与合并确认。

补充以下类型，同时核对实际 HTTP JSON：

- `SourceKind`、AI 草稿及其嵌套类型。
- 创建、整理、核对、修订请求。
- 健康检查、列表、详情、历史、审计和交接响应。

- 版本冲突和 422 的前端判别字段。

只暴露调用方必须知道的字段。数据库列、内部迁移字段和供应商原始响应不进入公开合同。

验收：A 不查看 `backend/` 就能写完请求和响应处理；`docs/API.md` 与类型文件没有互相矛盾的字段；`npm ci && npm run check:contracts` 在本地与 CI 通过。

### B4：与 A 完成一次浏览器接线

状态：B 侧自动化已完成，覆盖 CORS、token、重启、422、409、并发、持久化与完整 HTTP 闭环；真实浏览器证据必须由 A 的前端进入后共同完成。

按固定顺序联调：

1. 普通记录保存后立即显示“已保存”。
2. 普通记录整理、核对、查看详情和历史。
3. 修订后新旧记录都可追溯。
4. 生成并读取交接材料。
5. 危险原文显示顶部固定提醒。
6. 模拟 AI 失败，页面仍显示已保存原文、危险提醒和重试入口。
7. 制造旧版本提交，页面收到 409 后重新加载详情。
8. 刷新和后端重启后恢复记录；后端重启后重新获取 token。

验收：在真实浏览器中完成，不用临场修改数据库或代码。

## PR 规则

- 一个 PR 只交付一个垂直行为，不混入大规模格式化或框架迁移。
- PR 必须写：改了什么、A/C/D/E 要怎样接、实际运行了哪些检查。
- 接口变化必须在同一个 PR 更新实现、`docs/API.md`、`contracts/api.ts` 和测试。
- 不把测试失败改成跳过；不通过删除安全断言换取绿色结果。
- 任何改变原文、来源、时间、危险状态或历史不可变性的提议必须单独讨论，不能作为普通重构合入。

## B 的最终完成定义

B 完成不是“后端能启动”，而是同时满足：

- A 在浏览器完成最短闭环及 422/409 异常路径。
- HTTP 合同有完整类型和接口级回归。
- 幂等、版本竞争、修订历史、交接快照和重启恢复都可重复验证。
- C 更换 Mock/真实模型不会破坏原文先保存和失败响应。
- E 能从停止状态启动、演示、备份并恢复。
- 对外说明准确区分后端软件验证、真实模型验证、浏览器验收和临床验证。
